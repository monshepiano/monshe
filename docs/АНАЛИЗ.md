# Аудит кодовой базы JARVIS 1.2.0-beta.7

Полное прочтение всех модулей (бэкенд ~5 600 строк Python, фронтенд ~6 600 строк JS,
gateway, установщик, тесты). Ниже — все найденные ошибки, противоречия и мёртвый код.
Часть исправлена в этой же версии (отмечено ✅), часть описана как риск (⚠).

## 1. Настоящие баги (исправлены)

### 1.1 ✅ История диалога обрезается не с того конца
`db.get_messages(chat_id, limit=200)` делал `ORDER BY created_at ASC LIMIT 200` —
то есть возвращал **первые** 200 сообщений диалога, а не последние. В длинном
диалоге пропадали свежие реплики: и в интерфейсе после перезагрузки, и — хуже —
в контексте, который собирается для модели (`server._chat_stream` использует тот
же `get_messages`). Тот же латентный баг ломал `/api/replies`: подсказки
продолжения считались по первым 6 сообщениям диалога вместо последних. Теперь
берутся последние N с сохранением порядка ASC.

### 1.2 ✅ Кнопка «Проверить» в биллинге ничего не проверяла
Фронтенд слал `/api/billing?refresh=1`, сервер читал параметр `force` и всегда
получал пустую строку → «Проверить» и «Сохранить» отдавали закэшированные
данные и никогда не ходили в Cloud.ru. Сервер теперь понимает и `force`, и `refresh`.

### 1.3 ✅ Префиксная проверка путей вместо иерархической
Три места проверяли выход за каталог сравнением строк:
`str(path).startswith(str(base))` — `sandbox.safe_path` (граница безопасности
песочницы!), `server._serve_static`, `server._download`. Классическая ошибка:
путь `base/../abcX` резолвится в соседний каталог `…/abcX`, чьё строковое
представление **начинается** с `…/abc`, и проверка проходит. В песочнице это
давало доступ к каталогу соседнего диалога (`workspace/chats/<id>…`). Всюду
заменено на `Path.is_relative_to()`.

### 1.4 ✅ TypeError внутри инструмента выдавался за «неверные аргументы»
`tools.call` ловил `TypeError` как признак несовпадения сигнатуры, но `TypeError`
мог подняться из тела самой функции — и честная ошибка инструмента маскировалась
неверным диагнозом. Теперь аргументы проверяются через `inspect.signature.bind`
до вызова; `TypeError` из тела пробрасывается как обычная ошибка инструмента.

### 1.5 ✅ N+1 удаление сообщений при правке
`db.delete_messages_after` удалял строки по одной, с отдельным `commit` на каждую:
правка в длинном диалоге = десятки транзакций, а обрыв посередине оставлял
полусостояние. Заменено одной SQL-командой `DELETE … WHERE` с тем же условием
(`created_at > ? OR (created_at = ? AND id > ?)`).

### 1.6 ✅ Удаление диалога оставляло сирот
`db.delete_chat` чистил `messages` и `chats`, но не `questions` и `approvals`
этого чата. Ожидающая санкция удалённого диалога навсегда висела в панели
«Санкции». Теперь удаляются и они.

### 1.7 ✅ Отсутствие лимита на размер POST-тела
`Handler._body()` читал `Content-Length` байт в память без ограничения — любой
запрос (в т.ч. не из интерфейса) мог повесить процесс аллокацией. Плюс `_upload`
не проверял фактический размер декодированного файла: клиентская проверка «25 МБ»
обходилась прямым POST. Теперь: тело ≥ 48 МБ → 413; файл вложения ≥ 25 МБ → отказ.

### 1.8 ✅ CORS `*` на всех эндпоинтах
Любая страница в браузере пользователя могла прочитать `http://127.0.0.1:8765/api/messages`,
`/api/memory`, `/api/config` и отправить сообщение от его имени (приватность
локального приложения ломалась одним `<script>` на стороннем сайте). Теперь
CORS-заголовки выдаются только: запросам без `Origin` (не-браузерные клиенты),
`Origin` с localhost/127.0.0.1 и `Origin`, совпадающему с `Host` запроса
(обычный same-origin доступ, включая работу за прокси). Остальным — отказ.
Остаточный риск DNS-rebinding упомянут в §4.

### 1.9 ✅ `_compact_memory()` на каждый ход диалога
`db.recall()` запускал `_compact_memory()` — полное сканирование и повторную
канонизацию **всей** таблицы памяти. `recall` входит в `build_system_prompt`,
т.е. это происходило при каждом сообщении. Схлопывание алиасов — разовая
миграция качества, теперь выполняется один раз на процесс.

### 1.10 ✅ Рабочий цикл AUTO парсил JSON-логи задач каждые 2–10 секунд
`auto._loop` звал `db.list_tasks(60)`, который для каждой задачи разбирает
`events` (до 400 записей на задачу) — при 60 задачах это тысячи JSON-декодов
на каждый тик. Циклу нужны только `id/status/next_run`, для него добавлен
лёгкий `db.active_tasks()` без разбора events (UI продолжает получать полный
лог через `/api/tasks` и `/api/state`). Попутно порядок очереди стал честным:
прежде цикл обходил задачи от самой свежей, и при занятом слоте первой
запускалась последняя созданная задача (LIFO), а не первая в очереди.

## 2. Мёртвый код и противоречия (удалены/устранены)

- **`llm.embed()`** — не вызывается ни приложением, ни тестами. Embeddings в
  проекте фактически не используются (память сортируется по весу и времени).
  Удалён вместе с дублем кэша `_MODELS_CACHE` (список моделей теперь всегда
  выводится из единственного `_META_CACHE`).
- **Фронтенд `case 'chat_title'`** — сервер никогда не шлёт SSE-событие
  `chat_title` (название меняется после закрытия потока, список обновляется
  `loadChats()`). Мёртвая ветка удалена.
- **Фронтенд `case 'replies'`** — подсказки продолжения давно ходят отдельным
  REST-запросом `/api/replies`; SSE-событие `replies` никто не отправляет. Удалено.
- **Фронтенд `thinkTypeOld`** — заменена `thinkType`, определение осталось. Удалена.
- **`agent.run`, ветка `elif etype == "done": … pass`** — no-op. Удалена.
- **`auto._fmt_every`/`_fmt_in`** — дубликаты с разницей в одном префиксе.
  Объединены в `_fmt_interval(prefix, secs)`.
- **`auto.proactive_tick`** — путь с `_reserved=False` был недостижим:
  единственный прод-вызов — `proactive_async()` с `_reserved=True`
  (совместимость сигнатуры с тестами сохранена).
- **`ideas.refresh_async`** — имя обещает асинхронность, функция синхронная и
  дублирует проверку свежести внутри `refresh`. Сведена к одной функции.
- **`server.py`**: неиспользуемый импорт `socketserver`.
- **README «31 инструмент»** — в реестре 36 инструментов (+1 серверный
  sentinel `schedule_task`, который модели не выдаётся). Документация исправлена.
- **`orchestrator._choose_tier_raw(agent_mode, has_tools)`** — параметры
  принимаются, но не используются (маршрутизация сознательно не смотрит на
  тумблер AGENT). Оставлено как API, противоречие задокументировано здесь.

## 3. Оптимизации без смены поведения

- `sandbox.listing`: `sorted(base.rglob("*"))[:limit]` сортировал **всю** выдачу
  до обрезки — теперь обход ограничен лимитом.
- `db`: повторяющийся разбор `meta`/`args`/`events` вынесен в один хелпер.
- `Content-Disposition` в `_download`: имя файла экранируется
  (`urllib.parse.quote`) — кавычка в имени файла больше не ломает заголовок.

## 4. Осознанно НЕ изменённое (риски задокументированы)

- **DNS-rebinding**: проверка `Origin == Host` закрывает drive-by чтение локального
  API сторонними сайтами, но атакующий, полностью контролирующий DNS, может
  заставить браузер резолвить свой домен на 127.0.0.1 — тогда Origin совпадёт с
  Host. Полная защита — HTTPS на локальный сервер или проверка токена; для
  персонального приложения признано избыточным.
- **`agent.run()`** — метод ~700 строк с плотной gate-логикой (plan-gate, шлюз
  текстовых вызовов, ловушка вранья, UI-гейты). Он громоздок, но его событийный
  протокол стабилен, покрыт 76 тестами и Comentарием задокументированы гонки,
  которые уже были исправлены. Агрессивная перестройка ради «красоты» — высокий
  риск потерять качество; сделана только точечная чистка.
- **app.js одним файлом** — сознательное ограничение проекта «фронтенд без
  сборки». Разбиение на ES-модули возможно, но не даёт выигрыша при загрузке
  с локального сервера.
- **Опрос БД из `_wait_approval`/`_wait_answer`** (0.5–0.6 с) — оставлен:
  переживает обрыв SSE и работает между вкладками, что важнее экономии.
- **`config.load()` всегда сохраняет файл** — оставлено: миграции значений
  должны закрепляться на диске.
